# グラレコ手描き感の改善方針

## 背景と問題

殿より「HTMLファイルを作成してもらうときに、もっとビジュアル的なものにしてほしい。MCPを使えばどうにかなるか、または専用の描画ツールを作ってもいい」とのご下問。対話の中で的が絞られ、最終的な要求は「**グラレコでお願いしている手書き風の完成度を上げたい**」の一点に確定した。

## 調査で判明した事実

skill `graphreco-html` の references と、過去のグラレコ成果物7件を実測した結果、次が判明した。

- **揺らぎフィルタ（feTurbulence / feDisplacementMap）の使用回数が、過去7件すべてでゼロ**。`svg-snippets.md` に定義済みで、`enhancements.md` が「安価な底上げとして先に着手せよ」と明記していたにもかかわらず、一度も実行されていなかった。
- `svg-snippets.md` が「線は常に `stroke-width="2.5"`」と**線幅の固定を明文で強制**しており、筆圧の入り抜きに相当する表現が制度的に禁じられていた。
- 部品在庫は11点のみ。`<symbol id=` の点数はファイル間で3〜25と8倍のばらつきがあり、毎回ゼロベースで描き起こしている実態を示す。参照見本たる `claude-opus-5-graphreco.html` 自身がわずか3点。
- `css-skeleton.css` の既定フォントスタックが `"Segoe Print","Bradley Hand","Comic Sans MS",...` のままで、**殿の既出のご指摘「筆記体を避け可読な丸書体」が骨格ファイルに未反映**だった。
- 実レンダリングによる目視検分（信玄が `render_html.py` で実施）で、第1節・第2節にイラストが一点も無く、文字パネルと棒グラフのみである状態を確認。これは skill 自身の必須規約「各節に線画イラスト最低1点」への違反である。

**診断：能力不足ではなく、規約の未執行が主因。** 道具は既に揃っており、使われていなかった。

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| 案B | MCPサーバの導入 | **不採用。** グラレコHTMLは「外部参照ゼロの自己完結HTML」が既定方針であり、外部サーバから図や素材を取る方式と構造的に噛み合わない。またMCPが埋め得るのは素材調達・検証という下位層で、主因である線質・イラスト不在・フォントには届かない。全セッションに起動待ちと許可設定の負担を課す一方、効き目がここに無い |
| 案1 | rough.js を実行時にインライン埋め込み | 保留。実行時JS依存となり、JS無効で絵が消える。自己完結方針と部分的に衝突 |
| 案1' | rough.js を**ビルド時**に走らせ、揺れたSVGパスを焼き込む生成器 | **第2陣候補。** 実行時JSゼロ・外部参照ゼロを一切曲げずに線質を根治できる。「専用の描画ツールを作る」という殿のお考えの筋の良い実装形 |
| 案2 | SVGフィルタ／CSS拡充 | **第1陣で採用。** 規約は既に存在し、使っていないだけゆえ導入コストが極小 |
| 案3 | イラスト部品在庫の積み増し（20点） | 第3陣。1点15〜40分で計5〜13時間 |
| 案4 | 画像生成でイラストを作りdata URI埋め込み | **不採用。** 生成のたび絵柄が揺れ、現状の数少ない長所である統一感を自ら破壊する |
| 案5 | 検品の強化（チェックリスト＋実レンダリング必須化） | **第1陣で採用** |

## 決定と決め手

**第1陣として案2＋案5＋フォント是正を実施する。MCPは採らない。**

決め手は三点。

1. **最大の欠陥は能力不足ではなく規約の未執行**であり、「書いてあることを実行させる」ことが投資対効果で他のあらゆる案を圧倒する。過去7件でフィルタ適用がゼロだったのは、チェック項目が無かったためである。
2. **静的SVGであり続けることが、自己完結HTML方針との唯一の完全整合。** MCPも実行時JSも、この方針を削る方向にしか働かない。
3. **在庫は減価しない資産、生成は毎回ばらつく消耗。** 案4は統一感を壊す方向であり採らない。

## 殿の裁可（3点）

1. **着手範囲：第1陣のみ実施し、現物を見比べてから第2陣以降の可否を判断する。**
2. **崩しの許容度：「絵だけ崩す」。** 線画・枠線・装飾は大きく揺らして崩してよいが、テキストブロックの傾きと段組の整列は一切崩さない。可読性と密度を死守する。
3. **フォント：丸書体への是正のみ先行。** 和文手描きフォントのbase64埋め込み（ティアB）は今回は既定に格上げしない。

## 第1陣の実施内容

- `css-skeleton.css`：フォントスタックを筆記体排除・丸書体優先へ是正。Windows実機に `UDDigiKyokashoN-R.ttc`（UDデジタル教科書体N）が実在することを確認し、これを第一候補として採用可否を実レンダリングで判定中。当初 BIZ UDGothic 案が上がったが、角張ったUDゴシックでは事務文書の書体となり手描き感が消えるため信玄が差し戻した。
- `svg-snippets.md`：「常に2.5」の線幅固定規約を撤廃し、主線2.8〜3.4／通常2.2〜2.6／細部1.8〜2.2の三段階使い分け（同一シンボル内に最低2段階混在）へ改訂。揺らぎフィルタを既定適用へ格上げし、コピペ可能な完成形スニペットと適用例を明記。雛形サンプル7点自体も新規約に合わせて書き換え（規約本文だけ直しても実装者がコピペするのはサンプルの方であり、放置すれば定規的な線が再生産されるため）。
- `checklist.md`：手描き感チェック4項目（①フィルタ適用の有無 ②stroke-width が単一値でないか ③symbol点数が節数以上か ④筆記体フォントの混入）を、grepで機械的に確認できる形で追加。「各節に最低1点」を節番号ごとに一つずつ潰す形式へ変更。
- `enhancements.md`：フィルタ適用を「余裕があれば」から「実装最初の必須工程」へ格上げ。rough.js の条件付き許容の記述は第2陣に備えて維持。
- `SKILL.md`：`render_html.py` による実レンダリングと目視検分を必須工程として明記。完了条件を「チェックリスト通過まで」と明文化。「絵だけ崩す」の線引きを技術規約に追加。

## 実機で確認した事項（推論と区別）

- 信玄が `claude-opus-5-graphreco.html` を実レンダリングし、イラスト不在・定規的な線・欧文筆記体と和文ゴシックの不整合を目視確認。
- `C:\Windows\Fonts` に UDデジタル教科書体N が実在することを信玄が確認。
- 山県が揺らぎフィルタの scale 値を 0.5〜12 で段階的にレンダリング比較し、複数パス接合部は scale 4.5 以上で隙間が生じ、単一パスの枠線は 3.0 まで破綻しないことを実機確認。
- 山県がフォント全欠落時に `sans-serif` へ正しくフォールバックすることを故障注入で確認。
- 文字を含む親要素に直接 `filter` を掛けると文字の輪郭まで歪むため、`::before` 疑似要素に分離して枠だけに掛ける方式が有効であることを実機確認。

**未検証：** `baseFrequency` を変更した場合の見え方（今回は既存値のまま scale のみ検証）。
